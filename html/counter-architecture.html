Ganak — the Counter

Anatomy of count_loop() — the search, the component decomposition, the cache, and the count arithmetic. Everything above it is deliberately left out.

1. The main loop — the skeleton

Everything below is count_loop(). Stripped to its bones it is a two-part cycle: descend by carving the formula into independent components and deciding a variable in one of them, then ascend by combining sub-counts back up the stack. Conflicts short-circuit the descent; the rest of the page zooms into the two shaded boxes.

2. Descending — decide, propagate, analyse conflicts

This is the CDCL half, and it is close to a normal SAT solver: pick a variable, propagate, and on a conflict learn a 1-UIP clause and backjump. The counting-specific parts are that the branch variable is picked only from the current component, and that a conflict zeroes out the count of the branch it kills.

3. Ascending — components, cache, and the count arithmetic

The counting half, and what makes this a model counter rather than a SAT solver. Two rules govern everything: independent components multiply, the two polarities of a decision variable add. The cache is what makes it fast — a component whose count is already known is folded straight in and never searched again.

Search — decide, BCP, conflict analysis Decomposition — connected components Cache — lookup, store, invalidate Count arithmetic over the Field Optional / periodic

Every count is an FF — a CMSat::Field value produced by the FieldGen fg. Integers, rationals, complex rationals, MPFR complex floats, GF(2) parity, and polynomials over a finite field all flow through the exact same + and × above; the engine never knows which.

AspectDetail
KeyThe packed set of still-active variables and clause ids of the component, hashed with MurmurHash3 under a per-run random seed.
HitCount is folded immediately into the current branch via include_solution; the component is never pushed on the stack.
MissEntry is created but not yet inserted into the hash table — only entries that actually have a count get inserted.
StoreIn backtrack(), after both branches of the level are done and before the level is popped. For weighted counting the value is first normalised by the weights of component variables assigned at lower levels, so the entry is level-independent.
InvalidateOn backjump or a flipped decision literal, every descendant entry of the popped level is purged — those counts were computed under an assignment that no longer holds.
Disable--cache 0. Required when debugging wrong counts with CHECK_COUNT.
